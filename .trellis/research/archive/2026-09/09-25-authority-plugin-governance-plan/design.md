> 任务：`09-25-authority-plugin-governance-plan`
> 本文记录**治理方案的设计骨架与关键取舍**（给维护 Authority 的人看）。
> 逐主题的**规范条文**（给写消费者插件的人看）落在 `deliverables/01`~`03`。

## 一、设计边界

### 1.1 本设计要解决的结构问题

三家消费者各自的 `authority-adapter` / `AuthorityBridge` / `authority-store` 已经**事实上定义了契约**——
但定义在各自仓里、互不相通、且互斥（`research/01` E-V6）。本设计要做的不是"发明新契约"，
而是把这些隐式契约**提升为显式契约**，并给它一个**能被校验的载体**。

因此设计遵循一条硬纪律：**不新造机制**。每一条契约都必须落在既有载体上：

| 既有载体 | 可承担什么 | 出处 |
| --- | --- | --- |
| `shared-types` 的 TS 类型 | 公开面的**形状契约**（编译期） | `packages/shared-types/src/*.ts` |
| `docs/server/http-api.md` | 端点 / 鉴权 / 字段语义 | 已固化 |
| `docs/server/capabilities-and-isolation.md` | 能力矩阵（**当前已漂移**） | `research/02` E-C3 |
| 稳定 `code` 字符串 + `severity` | 状态与告警的机器可读表达 | `shared-types/src/modules.ts:264` 自注"stable strings" |
| `BUILTIN_JOB_REGISTRY_SUMMARY` | **字段级能力元数据**的登记范式 | `server-plugin/src/constants.ts` |
| L12 registry（`/registry/*`） | 已装扩展与其依赖集的只读视图 | `docs/server/http-api.md` §3.2/§4.8 |
| `.trellis/spec/` + `tavern-harness` 真源 | 治理规则的**约束力载体** | 见 §四 D5（待裁定） |

### 1.2 三篇交付物之间的接口

三主题不是并列的三篇文档，而是**有方向的依赖链**：

```
deliverables/01 接入契约
   │  定义「消费者怎么接」——含 init 形态、权限声明形态、降级形态
   │   ↓ 提供 R1.3 的「能力声明位」
deliverables/02 版本绑定
   │  定义「接的那个 Authority 够不够用」——consumer 声明需求，authority 回传标识
   │   ↓ 依赖 03 的「能力名与阶段」作为声明词汇表
deliverables/03 能力生命周期
      定义「能力怎么出生/长大/退休」——阶段枚举 + 单一真源 + 漂移门禁
```

三处**必须对齐的接缝**：

- **接缝 A（01→03）**：01 的 `declaredPermissions` 形态表必须与 03 的词汇表真源完全一致
  （否则 01 一发布就又是第 5 套词汇表）。→ 01 的该表**由 03 的真源生成或校验**，不独立维护。
- **接缝 B（02→03）**：02 若采用"按能力集声明需求"（D3），则能力名的权威来源是 03 的真源；
  02 不得自带能力名列表。
- **接缝 C（02→01）**：02 的不满足降级语义必须与 01 的降级最小必需行为**同源**，
  否则消费者需要实现两套降级逻辑。

**接缝 A/B 的落地约束**：两篇交付物中凡出现能力名清单，必须标注"以 `deliverables/03` §X 的真源为准"，
不得复制粘贴。

### 1.3 最小侵入原则（R6，用户 2026-09-25 追加 · 全局约束）

本设计产出的每一条契约方案都必须通过四道判定，否则改写或降级为"不做"：

| 判定 | 判定方式 | 违反时的处置 |
| --- | --- | --- |
| **纯增加** | 新增了什么？是否只新增只读字段 / 只读清单 / 断言？有改动既有字段语义或类型吗？ | 有改动 → 改写为新增字段 + 旧字段保留 |
| **零行为变更** | 现有 3 个消费者不改造时，行为是否与发布前逐字节一致？ | 否 → 该方案退回，只作为"需单独论证"的候选列出 |
| **单一 PR** | 能用一句话说清 PR 边界吗？（L1-MF-2） | 说不清 → 继续拆分或不做 |
| **可独立回滚** | 单独撤销该方案是否牵连其他方案？ | 牵连 → 拆分，或标为不可独立回滚并说明耦合点 |

**对本设计的直接影响 —— `protocolVersion` 兼容窗口（R2.4）**：
把 `!==` 精确相等改为区间判定是**改动既有判定逻辑**，直接违反 R6.1。
因此该方案**只能以「新增并行判定 + 保留旧判定」的过渡形态进入建议清单**：

```
新增：manifest 可声明 protocolVersionRange（缺省 = 不声明 = 走旧路径）
旧判定：protocolVersion !== AUTHORITY_MODULE_PROTOCOL_VERSION  → 原样保留、原样告警
新判定：仅在 manifest 声明了 range 时生效，且**只降级告警为 info**，不提升为阻断
```

即「新增一条更宽容的判定，与旧判定并行，旧判定行为一字不改」。
若最终无法构造出并行形态，则该方案**移出建议清单**，标为"需后续任务单独论证"（AC-14）。

**同源影响 —— 版本标识回传（R2.2）**：`SessionInitResponse` 增字段属**纯增加**，通过四道判定。
**能力集声明（D3）**：`AuthorityInitConfig` 增可选字段、真源新增只读清单，均属纯增加，通过。

## 二、关键设计决策（含推荐与代价）

### D1 · 契约真源放在哪一层

| 候选 | 优点 | 代价 |
| --- | --- | --- |
| **(a) TS 类型为真源**（`shared-types`） | 编译期即校验；改动走既有 8 步顺序；零新文件 | **JS 消费者读不到**——`ST-zip-converter` 是纯 JS，类型对它不存在；文档仍需手写 |
| **(b) 文档为真源** | 人能读；非 TS 消费者可读 | 文档与代码漂移无门禁（正是 `research/02` E-C3 的现状成因） |
| **(c) 机器可读清单为真源**（JSON/TS 常量），类型与文档皆派生 | 三方（TS 消费者 / JS 消费者 / 文档）同源；**漂移可被断言捕获** | 新增一个真源文件 + 一个校验脚本；需挂进质量门 |

**裁定（2026-09-25，用户选定 (c)）**：采纳机器可读清单为真源，TS 类型与文档皆派生，
且**复用既有范式**——`BUILTIN_JOB_REGISTRY_SUMMARY` 已经是一个"写在代码里、随 `features` 下发、
又被文档引用"的能力元数据真源。把它扩展到"能力清单 + 阶段 + 风险 + 文档锚点"，不必新造文件类型。
代价是需要在 `check:` 系列里加一条断言（见 D4）。

### D2 · 能力阶段枚举

**推荐 4 态**（不引入 `beta`/`rc` 等中间态，避免不可判定）：

| 阶段 | 含义 | 消费者可否依赖 | 准入条件 | 退出条件 |
| --- | --- | --- | --- | --- |
| `experimental` | 已实现并可用，但契约可能变 | 可以，但须容忍破坏 | 代码合并 + 有测试 | 有 ≥1 真实消费者稳定使用 → `stable`；或直接 → `removed` |
| `stable` | 契约冻结，破坏性变更须走废弃流程 | 可以 | 在 `experimental` 有真实消费 | 宣布废弃 → `deprecated` |
| `deprecated` | 仍可用，但已宣告将移除 | 可以，但应迁移 | 决定移除 | 过渡期满 → `removed` |
| `removed` | 已移除 | 不可 | 过渡期满 | — |

- 表达方式**复用既有范式**：与 `severity: 'error'|'warning'|'info'` 同为**稳定字符串 union**，
  TS 消费者可编译期穷尽，JS 消费者可字符串比较（`modules.ts:264` 已确立该范式）。
- **`removed` 是否保留在真源里**：推荐保留（带 `since` / `removedIn`），以便漂移检查能识别
  "文档里消失了但代码还在引用"与"代码删了但文档还写着"两个反向漂移。

### D3 · 版本绑定的表达方式

| 候选 | 优点 | 代价 |
| --- | --- | --- |
| **(a) 语义版本区间**（`requiredAuthorityVersion: ">=1.7.0"`） | 直觉；工具链成熟（semver） | **Authority 的四套版本号都不描述公开 API 兼容性**（`research/01` E-V5），给它们加 semver 语义等于先定义"何时该 bump"，而这本身就是未决的（`research/01` 未验项 1） |
| **(b) 能力集声明**（`requiredCapabilities: {sql: 'stable', blob: 'stable', agent: 'experimental'}`） | 直接对应消费者真实需求；与 D2 的词汇表同源；不受版本号纪律未定之困 | 声明更长；消费者需知道能力名 |
| **(c) 两者并存**（版本作粗筛，能力集作精判） | 粗筛能挡住明显错配 | 两套语义都要维护；且版本粗筛的语义未定义 |

**裁定（2026-09-25，用户选定 (b)）**：以**能力集声明**为契约主体，版本号仅作诊断信息回传
（answer「你连的是谁」而不 answer「够不够」）。
理由：消费者真正关心的是"我要用的那几个能力现在能不能用"，不是"对面是 1.6.8 还是 1.7.0"。
`(b)` 也天然消解了 `research/01` E-V5 的困境——不必先定义版本 bump 纪律才能发布契约。

**同时必须补上**：`SessionInitResponse` 回传 Authority 自身标识（供排障与安全中心展示），
以及 `protocolVersion` 由**精确相等改为显式兼容区间**（`research/01` E-V4／R2.4）——
后者是独立于 D3 的必修项，因为它当前是"bump 即全量失效"。

### D4 · 漂移检查挂在哪

- 既有质量门：`npm run typecheck` → `npm test`（vitest + cargo）→ `npm run bench:core` → `npm run check:installable`。
- **推荐**：新增一条断言测试（落在 `packages/server-plugin/src/` 或 `packages/shared-types/` 的既有测试文件中，
  不新建管线），断言"真源清单的每一项都在 `docs/server/capabilities-and-isolation.md` 有条目"。
  这样它天然进入 `npm test`，无需改 CI。
- **代价**：文档变成构建依赖——改真源不改文档会**测试失败**。这是**有意为之**（E-C3 的漂移正是因此长期存活）。
- **回滚点**：该断言是独立测试文件/独立 `it()`，失败时可直接定位到"文档未同步"而非产品缺陷。

### D5 · 契约的约束力载体 —— **已裁定 (b)**

| 候选 | 效果 | 代价 |
| --- | --- | --- |
| (a) 仅在任务目录 `deliverables/` | 同 09-22 形态；零外溢风险 | 随任务归档而**不可见**；对其他 15 仓零约束力——复现 P-1（真源不在会被推送的版本库里 → 整体消失） |
| **(b) 任务目录 + `.trellis/spec/`** | 本仓后续会话与协作者可读；`.trellis/spec/` 已随 `27467d6` 纳入 git，每次提交推送 | 只覆盖 Authority 本仓；不直接约束其他消费者仓 |
| (c) (b) + 同步进 `tavern-harness` 真源 | 对 16 仓具备约束力 | 需改真源仓并跑同步器；契约与规则块同仓，规则块会变长 |

**裁定（2026-09-25，用户选定 (b)）**：交付物落在任务目录，同时在 Phase 3（3.3 spec update）
把**已成文的规范条文**同步进 `.trellis/spec/`。

- **落点建议**（实施时确认具体文件）：
  - 接入契约 → `.trellis/spec/sdk-extension/frontend/`（消费者视角，SDK 接入面）
  - 能力词汇表与漂移门 → `.trellis/spec/shared-types/backend/`（真源在 shared-types）
  - 版本绑定与兼容窗口 → `.trellis/spec/server-plugin/backend/`（会话与协议版本在 server-plugin）
- **明确不做**：本次**不同步进 `tavern-harness` 真源**（候选 (c) 未选）。
  跨仓约束力的缺口作为**后续任务的输入**登记，不在本任务内解决。

## 三、兼容性与迁移

- **对现有 3 个消费者的影响**：契约发布**不改变任何既有行为**（纯文档 + 后续才可能加字段）。
  接入契约中的"已知偏离项"只作清单，不构成改造要求。
- **对 L12 registry 的影响**：接缝 A 要求 01 的权限形态表与真源一致；
  L12 registry 现用的 `AuthorityCapability`（10 项扁平）是 D2/D3 词汇表的**天然候选**，
  但需先解决它与权限资源（11 项）的映射缺表问题（`research/02` E-C6）。
- **对 Companion Module `protocolVersion` 的影响**：R2.4 的兼容窗口方案若落地，
  须同时改 `companion-module-loader-service.ts` 的门禁与 `extension-registry-service.ts` 的两处判定——
  **属后续任务的实施范围**，本任务只出方案。
- **迁移顺序**（后续任务的建议顺序，供本任务交付物引用）：
  ① 能力真源 + 漂移门（无消费者可见变更）→ ② 版本标识回传 + 兼容区间 →
  ③ 消费者按新契约改造（逐仓，可独立回滚）。

## 四、明确不做

1. **不实现任何产品代码**（含真源文件、断言、字段）——本任务止于设计。
2. **不重定义权限模型**——`SUPPORTED_RESOURCES` 的 11 项与风险/默认策略表是既有事实，本设计只做登记与防漂移。
3. **不设计 Host Bridge 跨宿主策略**（L0-12 已硬规定）。
4. **不重复 09-22 的宿主侧 PR 拆分**。
5. **不引入外部依赖**（不引 semver 库、不引 schema 校验库）——若 D3 选 (b)，契约本身不需要 semver。
6. **不改 `docs/server/` 文件**（AC-11 要求零改动）；文档侧发现的问题只作为**待办清单**输出。
