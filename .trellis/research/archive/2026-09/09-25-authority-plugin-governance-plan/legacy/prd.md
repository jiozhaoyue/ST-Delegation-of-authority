# Authority 后端与前端插件协同治理规划

## Goal

把 Authority 从「四个消费者各自猜契约」推进到「一份公开的协同契约」：产出**三篇规划文档**，让仓群里的插件作者能回答三个问题——
「我该怎么接 Authority」「我怎么知道我的 Authority 版本够不够」「Authority 改能力时我怎么被通知」。

**用户价值**：当前 3 个真实消费者 + 1 个在途消费者（`ST-chatfilesys-rebuild`）规模可控，是发布契约的窗口期。
契约缺位的代价已经实际发生（同一份 SDK 的两家消费者对同一返回形状得出互斥结论，见 `research/01` E-V6），
不收敛则随消费者数量线性放大。

**本阶段只产出规划文档，不实施产品代码。**

---

## Background

### 已确认事实（全部带 file:line 回源，详见 `research/`）

1. **消费者盘点是确定的、可穷尽的**：仓群 16 仓全量检索，**3 个真实消费者**
   （`SillyTavern-Timelines` / `ST-BgLoader` / `ST-zip-converter`）+ **1 个在途**
   （`ST-chatfilesys-rebuild`，仅有 `backend-plugin-spec.md`）+ 本仓官方示例 `packages/example-extension`。
   其余 11 仓零命中。（`research/00` §一）
2. **版本绑定机制不存在**：`AuthorityInitConfig` 无"所需 Authority 版本"字段；
   `SessionInitResponse` 不回传 Authority 自身版本；SDK 内 `version` 仅一处透传，无比较逻辑。
   唯一的版本门禁是 Companion Module `protocolVersion` 的**整数精确相等**判定（bump 即全量失效，无兼容窗口）。
   （`research/01` E-V1/V2/V3/V4）
3. **公开面契约大量未固化**：`storage.kv` / `storage.blob.put` / `storage.blob.get` 的返回形状
   **均无权威契约**——zip-converter 写 3~7 路分支容错并自注"未在 README 固化"，BgLoader 反其道写单路强类型断言。
   两者不可能同时正确。（`research/01` E-V6）
4. **能力可用性有接口、零消费**：`client.getCapabilities()` 存在但三家消费者无一调用；
   BgLoader 改为**硬编码** `agentTools:true`，而它从未声明 `agent.browser` —— 实证缺陷。（`research/00` §2.5）
5. **能力演进无生命周期**：全仓检索 `deprecat|弃用|废弃|experimental` **零命中**，能力只有"存在/不存在"两态。
   （`research/02` E-C2）
6. **三载体已漂移**：`SUPPORTED_RESOURCES` 有 **11** 项资源并配了风险等级与默认策略，
   而权威文档 `docs/server/capabilities-and-isolation.md` §1/§2 **只登记 8 项**——
   `module.execute`、`agent.run`、`agent.browser` 在该文档**零命中**。
   其中 `module.execute` 在整个 `docs/server/` 全仓无文档，却默认 `granted`。（`research/02` E-C3）
7. **四套能力词汇表并存、无映射表**：权限资源 11 项 / Feature Flags ~28 布尔 / 注册表能力 10 项 /
   宿主矩阵键 9~10 项；唯一的 ①→③ 映射是函数体内硬编码 `if` 链，且 `module.execute` 的跳过决策
   **只存在于一句代码注释**中。（`research/02` E-C6）
8. **无一致性门禁**：`npm run build` / `npm test` / `check:installable` 均不校验文档与代码一致，
   故第 6 条的漂移能被长期保留。（`research/02` E-C4）
9. **前序边界**：09-22 已定宿主侧（ST/Luker）PR 拆分方案并获确认；本任务**不重叠**该范围
   （那是宿主改造，本任务是 Authority 侧契约）。

### 用户裁定（2026-09-25）

- 产出范围：**纯规划文档**（同 09-22 形态），不写产品代码。
- 主题优先级（三项全选）：跨仓库兼容与版本绑定 / 能力演进生命周期 / 消费者盘点与接入契约。
- 执行方式：**全部主代理执行，不派子代理**。
- 分批 PR 与实际回提：**不在本次范围**。
- **契约固化载体**：任务目录 `deliverables/` **+ `.trellis/spec/`**；本次**不同步**进 `tavern-harness` 真源
  （跨仓约束力缺口登记为后续任务输入）。（`design.md` D5）
- **契约真源层**：**机器可读清单为真源**，TS 类型与文档皆派生；复用
  `BUILTIN_JOB_REGISTRY_SUMMARY` 的既有范式，不新造文件类型。（`design.md` D1）
- **版本绑定表达**：**能力集声明**为主体，版本号仅作诊断信息回传。（`design.md` D3）
- **最小侵入**：一切不改产品代码，**只增加绑定等声明**；最小侵入、PR 可控（2026-09-25 追加，见 R6 / AC-13 / AC-14）。

`design.md` D2（能力阶段 4 态模型）为推荐方案，随本次规划一并审阅确认。

## Requirements

### R1 · 消费者盘点与接入契约（→ `deliverables/01`）

- R1.1 穷尽盘点仓群 16 仓的 Authority 消费者，产出逐仓判定表（含"零命中"结论），
  并覆盖在途消费者与官方示例扩展。
- R1.2 对每个真实消费者产出**逐维对照表**：身份、`init` 入参、`declaredPermissions` 形态、
  降级策略、返回形状解析方式、能力可用性查询方式。
- R1.3 产出**接入契约规范**（normative）：一次 `init` 的正确形态、`declaredPermissions` 的合法形态表
  （含 `http.allow` / `events.channels` 这类带参声明的写法）、降级的最小必需行为（含冷却与自愈要求）。
- R1.4 明确「已知偏离项」清单：现存消费者中不符合该契约的具体位置与后果（如 BgLoader 的 `uiLabel` 误读、
  `agentTools` 硬编码、`initPromise` 永久缓存导致无法自愈），供后续改造参考，**但本任务不改造消费者仓**。

### R2 · 跨仓库兼容与版本绑定（→ `deliverables/02`）

- R2.1 产出**版本面现状图**：四套版本号（plugin/sdk/core/hostBridge）、`protocolVersion`、
  `features.registryVersion` 各自的语义边界与现有 bump 纪律（未明的须标"未明"）。
- R2.2 产出**版本绑定契约草案**（字段级）：消费者如何声明所需 Authority 版本（或所需能力集），
  Authority 如何回传自身可绑定标识，不满足时双方的**显式降级**语义（禁止静默失效）。
- R2.3 产出**公开面契约固化清单**：逐条列出当前无权威契约的返回形状（`storage.kv` get、
  `storage.blob` put/get 等），给出应固化的形状与固化载体。
- R2.4 产出 `protocolVersion` 破坏性 bump 的**兼容窗口方案**：如何避免"bump 即全量失效"。
- R2.5 产出**三个现有消费者按新契约的改造点清单**（逐条含位置与理由），作为后续任务输入——
  本任务只出清单，不实施。

### R3 · 能力演进生命周期（→ `deliverables/03`）

- R3.1 产出**能力阶段模型**：定义阶段枚举与其准入/退出条件，并说明与既有范式
  （L12 registry 的稳定 `code` + `severity`；`BUILTIN_JOB_REGISTRY_SUMMARY` 的字段级登记）如何复用而非新造。
- R3.2 产出**能力登记载体方案**：解决四套词汇表并存（`research/02` E-C6），
  给出单一真源 + 派生视图（或显式映射表）的方案，并说明各派生视图的生成/校验方式。
- R3.3 产出**漂移防护机制**：把第 6/8 条的事实（文档与代码不一致、无门禁）转为可执行的检查项
  （例如"11 项资源必须全部出现在权威文档"），并指明该检查应挂在哪个既有质量门。
- R3.4 产出**能力废弃流程**：旧消费者如何被通知、过渡期如何定义、何时可硬删。
- R3.5 把 `module.execute` 的跳过决策（当前仅在代码注释）与 `agent.*` 的文档缺位，
  作为规范化登记的首批输入复现为可复核证据。

### R4 · 证据纪律（跨三篇的元要求）

- R4.1 每条结论必须回源到 `research/00`~`02` 的 E 编号或 file:line。
- R4.2 每篇末尾必须显式登记**未验项**，不得隐藏。
- R4.3 不得把"风险判断/推论"表述为"实测结论"，二者须在文中可区分。

### R5 · 边界声明（三篇均须遵守）

- 不写产品代码；不向上游提 PR；不修改任何消费者仓；不遍历 `Instance/**`；不重新设计 Host Bridge 跨宿主策略（L0-12 已定）。

### R6 · 最小侵入原则（用户 2026-09-25 追加，约束三篇的全部设计产出）

三篇交付物提出的**每一条**契约方案，都必须满足以下四条可判定条件，否则须改写或降级为"不做"：

- R6.1 **纯增加**：只以**新增声明**表达（新增只读字段、新增只读清单、新增断言）。
  **不改**既有字段的语义或类型、**不改**既有判定逻辑、**不改**既有消费者行为。
- R6.2 **零行为变更**：契约发布本身不改变任何已在运行的路径。
  现有 3 个消费者在不改造的情况下，行为与发布前逐字节一致。
- R6.3 **可独立成 PR**：每条方案须能切成一个**单一功能 PR**（L1-MF-2），
  一句话说清边界；说不清即为未拆分完成。
- R6.4 **可独立回滚**：每条方案须能单独撤销而不牵连其他方案；须在交付物中写明回滚点。

**推论（须在交付物中体现）**：凡方案需要改动既有判定逻辑（例如 `protocolVersion` 由精确相等改为区间），
**必须**同时给出「新增一条并行判定、保留旧判定」的过渡形态——
否则违反 R6.1/R6.2，该方案不得进本任务的最终建议清单，只能作为"需要在后续任务中单独论证"的候选项列出。
