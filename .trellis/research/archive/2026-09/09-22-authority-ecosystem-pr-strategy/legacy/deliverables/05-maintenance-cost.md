## 一、"地狱"的机理（先看清循环长什么样）

```
给宿主打补丁 → 宿主升级追补丁 → PR 等待期"插件版 + 补丁版"双份维护
→ 多宿主 × 多插件的联动面按 N×M 发散 → 每个上游拒收都沉淀为长期私有分叉 → 累死
```

叠加 P-1 类风险：为省事把"协同知识"（依赖关系、可用性、约定）放在不推送的地方 → 静默消失，协作退回口头。

**破局思路：不是少提 PR，而是让每个环节的失败都不产生持续维护负担。**

---

## 二、八条策略

### S1 单一能力供应商：后端只进 Authority 一个口

需要服务端能力的插件一律走 Authority 可移植子集（`04-portable-subset.md`），**不自造第二后端**（`03-backend-route.md` 裁定）。
效果：插件 × 后端的联动面从 N×M 收敛为 **N+1**——宿主/后端演进只对齐一处。

### S2 契约优先，实现后置

插件之间、插件与 Authority 之间只经**声明契约**通信：
- 插件互调：Companion Modules transaction（`client.tx('<moduleId>:<txName>')`，`research/04` §6.2(e)）——绝不 import 对方内部实现；
- 能力检测：Feature Flags 26 路径（§6.2(a)）——上游加功能不破坏旧调用；
- 类型演进：`shared-types` 单一类型真源 + `AUTHORITY_MODULE_SCHEMA_VERSION=1` 版本协商。
效果：对方改实现不破我，我也不必盯着对方源码（P-13 反面）。

### S3 毕业制 PR：插件是完整交付，PR 只是收编

新功能先在插件里长（0 上游成本）→ 需求稳定 + 实测数据 → 才提炼为单一功能 PR。
**铁律：任何插件功能不得依赖 PR 被合入才能工作**（`01` 号文 A3）。
效果：上游节奏与插件节奏解耦——上游慢/拒，插件用户无感。

### S4 宿主差异收进桥接层

宿主差异判断集中在唯一 host-bridge 模块（L0-9），业务层只见可移植子集；跨宿主插件直接不碰桥接面（L0-12）。
效果：宿主升级的适配成本收敛在 Authority 一处，不扩散到各插件。

### S5 分叉寿命 = PR 生命周期

- `fetch upstream` + `--ff-only` 对齐；从 `upstream/main` 切短分支 `pr/<host>/<scope>-<thing>`；推 `origin`；合并/拒收后**删分支**（`02` 号文总纲 3）。
- 绝不 `git push upstream`（L1-MF-1）；不用 `reset --hard` 排障（L0-7）。
- Luker 侧急用补丁走 Dev/Luker fork 仓，ST 合入后**删除私有补丁**（`02` 号文 §四）。
效果：仓库里不存在"活着但没人管"的分叉。

### S6 拒收预案：提出 PR 时就预设"被拒也不难受"

| PR 结果 | 动作 |
| --- | --- |
| ✅ 合入 | 删分支；Luker rebase 自然继承 |
| ❌ 拒收、诉求成立 | 功能**留在插件形态**长期维护（插件本就全功能）；登记 won't-fix，不再追 |
| ❌ 拒收、诉求弱 | 放弃并记录原因，不纠缠 |
| 😴 issue 无响应 | issue 挂 2 周无回应即暂停 PR 计划，转插件形态；插件验证出强数据后再重启 |

**禁止**："PR 被拒 → fork 长期背补丁追宿主版本"——这正是地狱的第一环。

### S7 PT/TT 成本封顶

PT/TT 无服务端插件基建（`research/07` §2.5）→ **不为它们自造后端**；插件提供纯前端降级（功能子集全保留，L0-11）即止。
效果：生态抱负不再额外支付"第四宿主"的全套成本。

### S8 跨仓联动红线

任何改动若需**同时改 >2 个仓**才能交付 → 视为设计问题回炉（应收敛为插件或契约）。联动面必须经契约（S2）而非"人肉同步多个仓"。
配套：检索先行（L0-3）防自造轮子；测试即质量门（L0-13）防回归反复烧成本。
