  - 用户的 GPT5.5 重构版 https://github.com/jiozhaoyue/SillyTavern-Timelines

**核心概念设计（需自洽性审查）：**

- 现状问题：原生 jsonl 里聊天是**线性**的，分支只改变**楼层内容**、不改变走向；每个消息的每个分支上下关系**不绑定**；真正的剧情走向靠**聊天文件**区分（创建分支/检查点）。导致聊天文件之间存在**一大堆重复历史**。
- 新概念：**消息的分支分组**。原本 jsonl 系统把一个消息视为一个分支分组；**每一个相邻分支分组之间存在绑定关系**（解耦/重绑定在酒馆设计里是无感的，如删除消息、上下移消息）；组内分支可随意对应。
- **绑定关系**定义：指分支分组作为相邻楼层的关系。改变了即为**解绑**，同时分支分组与新的相邻楼层的分支分组**绑定**。
- 系统目标：使**一个楼层可以有多个分支分组**，可随意创建、更改分支所属分支分组，编辑相邻消息的分支分组的绑定关系。
- **jsonl 合并规则**：完全遵守以上——把一个聊天文件中的消息视为一个分支分组，与相邻分支分组（原消息）绑定；**完全相同的聊天分组直接合并**；不同的合并到**同一层楼但不同分支分组**；绑定关系遵循以上。
- **分支**：指分支分组间的绑定关系。一个分支分组**只能和一个父级分支分组**（上一层楼的其中一个分支分组）绑定，**可以绑定多个子级分支分组**（下一层楼的分支分组）。
- ❓**切换分支**：应当是有**联动**的 —— "我切换了这个父级分支分组为这个楼层的另一个，那个，这个效果我不知道该怎么说，怎么描述"。
- **聊天分支树状图**：参考 timeline 插件设计，也参考各种聊天文件分支可视化；应可选择**向右或向下展开**；每个节点可选择显示：**分支标题**（一般为 AI 对这一条聊天的总结 / 这条分支 / 或默认自动分配序号）。
- ❓**模式**：需要提供模式 —— ①一个分支分组只有一个分支；②再加上"一个分支分组只能绑定一个子级分支分组"。用户原话："这个模式我不知道该怎么说……反正我不知道，需要讨论"。

**功能表：**

| 序号 | 功能 | ui 设计 |
| --- | --- | --- |
| 1 | jsonl 文件映射，即用即生成，原样保存 | |

### B10. luker DEV PR（全部针对**云和移动端交互**进行改进）

1. **数据库设置应当完全遮住**，支持**手势回退**，不会触及聊天界面；**强制屏蔽侧拉回退操作**，防止移动端误触回退至临时聊天界面。
2. **允许拖拽预设**，增加**智能分类**。
   - 附：**酒馆宿主源码改造方案（另行走 Dev/Luker 仓库交付，不进本插件）**——两个宿主的备份端点都是 `archiver('zip')` 默认 deflate-6，改法一行级：
     ```js
     // src/users.js — createBackupArchive 内
     const archive = archiver('zip', { store: true });
     // 或保留可配：const archive = archiver('zip', { zlib: { level: getConfigValue('backups.zipLevel', 6) } });
     // config.yaml: backups.zipLevel: 0 即 store
     ```
     `store: true` 后服务端只做"读文件→塞容器"，不再压 deflate。备份包体积变大（聊天 json 压缩率高，但图片/sqlite 本来就压不动），TTFB 和传输速度直接受限于磁盘+网络，千兆内网基本跑满。建议做成 `config.yaml` 的 `backups.zipLevel` 配置项（0~9），默认 0 或 1。改完走 Docker 镜像重建或 git pull 实例。**这是收益最大的一刀，但不属于本插件交付范围**，本插件的提速在下方不依赖它。
3. **针对扩展页面补丁**：懒扫描更新，记录上次扫描，时间短则直接显示缓存的 url，可以**手动扫描**，防止每次进扩展页面扫描。
4. 查看 **luker 多 agent**，然后 **grill-me(with-docs) for sillytavern**（或者叫 `request_user_input for sillytavern`）。
